<h1>Transactions and ACID Guarantees</h1>
<p>Concurrent queries and sudden crashes constantly threaten data integrity. A database transaction wraps multiple SQL statements into a single indivisible contract: either every change lands safely with <code>COMMIT</code>, or every partial trace vanishes with <code>ROLLBACK</code>.</p>
<div class="summary-strip">
  <div class="pill-box"><span class="pill-label">Core Contract</span><strong>All-or-Nothing (Atomicity)</strong></div>
  <div class="pill-box"><span class="pill-label">Persist</span><code>COMMIT</code> flushes to WAL on disk</div>
  <div class="pill-box"><span class="pill-label">Undo</span><code>ROLLBACK</code> reverts partial work</div>
  <div class="pill-box"><span class="pill-label">Concurrency</span><strong>4 SQL Isolation Levels</strong></div>
</div>

  <h2 id="h-lifecycle">Why Transactions Exist &amp; How They Execute</h2>

  <h3>Worked Example · \$100 Transfer Step-by-Step</h3>
  <ol class="step-trace">
    <li><strong><code>BEGIN TRANSACTION</code></strong>: the engine assigns a transaction ID and acquires write locks on affected rows so no rival session reads half-finished balances.</li>
    <li><strong><code>UPDATE accounts SET balance = balance - 100 WHERE id = 1</code></strong>: the before-image is recorded in the Write-Ahead Log (WAL) before modifying data pages.</li>
    <li><strong><code>UPDATE accounts SET balance = balance + 100 WHERE id = 2</code></strong>: if a constraint or network error hits here, the engine replays the undo log backward.</li>
    <li><strong><code>COMMIT</code></strong>: WAL records flush sequentially to disk (Durability), making both updates atomic and visible to everyone else.</li>
  </ol>
  <pre><code>BEGIN TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
SAVEPOINT after_debit;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
-- ROLLBACK TO SAVEPOINT after_debit;  -- reverts only the credit if needed
COMMIT;</code></pre>
  <div class="compare-grid">
    <div class="compare-box bad">
      <strong>❌ Common Mistake</strong>
      Leaving <code>BEGIN TRANSACTION</code> open inside application error handlers without calling <code>ROLLBACK</code> holds row locks indefinitely and stalls other users.
    </div>
    <div class="compare-box good">
      <strong>✅ Right Way</strong>
      Always wrap transactional blocks in <code>try { ... COMMIT; } catch { ROLLBACK; }</code> so locks release immediately on failure.
    </div>
  </div>
  <details class="oral-check">
    <summary>Exam Defense: Power is lost 1 ms after the client receives COMMIT confirmation. Are the rows safe?</summary>
    <div class="oral-ans">Yes. Thanks to <strong>Durability</strong> and <strong>Write-Ahead Logging (WAL)</strong>, the engine guarantees log records hit non-volatile disk <em>before</em> reporting COMMIT success, allowing crash recovery to redo any un-flushed data pages on restart.</div>
  </details>
  <div class="key-takeaway"><strong>Key takeaway:</strong> Never confuse <em>Atomicity</em> (all-or-nothing execution) with <em>Durability</em> (surviving crashes once committed).</div>
</section>

<section class="card" id="t-isolation">

  <h2 id="h-isolation">Concurrency Anomalies &amp; Isolation Levels</h2>
  <p>Running every transaction strictly one after another guarantees safety but kills throughput. SQL isolation levels let you tune the exact trade-off between concurrency speed and read anomalies.</p>
  <table>
    <thead><tr><th>Isolation Level</th><th>Dirty Read</th><th>Non-Repeatable Read</th><th>Phantom Read</th></tr></thead>
    <tbody>
      <tr><td><code>READ UNCOMMITTED</code></td><td>Possible</td><td>Possible</td><td>Possible</td></tr>
      <tr><td><code>READ COMMITTED</code></td><td>Prevented</td><td>Possible</td><td>Possible</td></tr>
      <tr><td><code>REPEATABLE READ</code></td><td>Prevented</td><td>Prevented</td><td>Possible (standard)</td></tr>
      <tr><td><code>SERIALIZABLE</code></td><td>Prevented</td><td>Prevented</td><td>Prevented</td></tr>
    </tbody>
  </table>
  <div class="callout trap"><strong>Exam trap:</strong> Students confuse <em>Non-Repeatable Read</em> (an existing row's column value changes between two reads) with <em>Phantom Read</em> (a brand-new row matching your <code>WHERE</code> clause suddenly appears on the second run).</div>
  <div class="key-takeaway"><strong>Key takeaway:</strong> <code>READ COMMITTED</code> blocks dirty reads; only <code>SERIALIZABLE</code> stops all three anomalies under the ANSI SQL standard.</div>
</section>
