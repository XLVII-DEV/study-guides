Transactions and ACID Guarantees

Concurrent queries and sudden crashes constantly threaten data integrity. A database transaction wraps multiple SQL statements into a single indivisible contract: either every change lands safely with COMMIT, or every partial trace vanishes with ROLLBACK.

Why Transactions Exist & How They Execute

Imagine transferring \$100 from Account A to Account B: without a transaction wrapper, a power cut between the debit and the credit destroys money in production.

Worked Example · \$100 Transfer Step-by-Step

  1. BEGIN TRANSACTION: the engine assigns a transaction ID and acquires write locks on affected rows so no rival session reads half-finished balances.
  2. UPDATE accounts SET balance = balance - 100 WHERE id = 1: the before-image is recorded in the Write-Ahead Log (WAL) before modifying data pages.
  3. UPDATE accounts SET balance = balance + 100 WHERE id = 2: if a constraint or network error hits here, the engine replays the undo log backward.
  4. COMMIT: WAL records flush sequentially to disk (Durability), making both updates atomic and visible to everyone else.
BEGIN TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
SAVEPOINT after_debit;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
-- ROLLBACK TO SAVEPOINT after_debit;  -- reverts only the credit if needed
COMMIT;
❌ Common Mistake Leaving BEGIN TRANSACTION open inside application error handlers without calling ROLLBACK holds row locks indefinitely and stalls other users.
✅ Right Way Always wrap transactional blocks in try { ... COMMIT; } catch { ROLLBACK; } so locks release immediately on failure.
Exam Defense: Power is lost 1 ms after the client receives COMMIT confirmation. Are the rows safe?
Yes. Thanks to Durability and Write-Ahead Logging (WAL), the engine guarantees log records hit non-volatile disk before reporting COMMIT success, allowing crash recovery to redo any un-flushed data pages on restart.
Key takeaway: Never confuse Atomicity (all-or-nothing execution) with Durability (surviving crashes once committed).

Concurrency Anomalies & Isolation Levels

Running every transaction strictly one after another guarantees safety but kills throughput. SQL isolation levels let you tune the exact trade-off between concurrency speed and read anomalies.

Isolation LevelDirty ReadNon-Repeatable ReadPhantom Read
READ UNCOMMITTEDPossiblePossiblePossible
READ COMMITTEDPreventedPossiblePossible
REPEATABLE READPreventedPreventedPossible (standard)
SERIALIZABLEPreventedPreventedPrevented
Exam trap: Students confuse Non-Repeatable Read (an existing row's column value changes between two reads) with Phantom Read (a brand-new row matching your WHERE clause suddenly appears on the second run).
Key takeaway: READ COMMITTED blocks dirty reads; only SERIALIZABLE stops all three anomalies under the ANSI SQL standard.
